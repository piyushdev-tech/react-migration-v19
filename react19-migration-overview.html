A migration system that can be paused and resumed by anyone, anywhere.

Why it's built this way

Breaking changes first, not feature adoption

Three decisions shape every phase that follows.

Verify live Peer ranges, TypeScript floors, and vulnerability baselines shift faster than training data — every check hits the real registry or repo, never memory.
Fix what broke, not what's new Actions, the compiler, Server Components are out of scope unless explicitly asked for. This is remediation, not a feature tour.
Assume interruption Token limits, handoffs, a colleague on another machine — the workflow checkpoints after every phase so a stop is never a restart.

Architecture

Six files, each with one job

One entry point, two stages, a shared state file, and a driver that can run the whole thing unattended.

Stage 1 · read-only

Planning — assessment only

Nothing here touches source code. This is the entry point for every request, including ones that just ask "is it safe to upgrade."

0Baseline
Clean tree, dedicated branch, a true React-18 test/build baseline, and migration scope decided. no mutation
1Peer-dependency matrix
Every dependency classified ✅ / 🟡 / 🔴 / ⚪ against the live React 19 peer range. no mutation
2TypeScript compatibility
Dist-tag check finds the real @types/react floor for the installed TypeScript. no mutation
3Vulnerability & stability
npm audit baseline; prefer the smallest stable version over blindly installing latest. no mutation

Stage 2 · mutates code

Implementation — fix, verify, ship

Only reached once Stage 1 is fully green. Every fix here is applied by hand — no automated rewrite tool is used or depended on.
